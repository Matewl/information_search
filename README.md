# L₀: булевый и координатный поиск на C++17

Движок напрямую читает Parquet среза FineWeb-Edu **CC-MAIN-2014-10**, строит
сегментный обратный индекс и исполняет булевы и позиционные запросы. Перед
индексацией документы глобально сортируются по `score` по убыванию; термы
нормализуются английским стеммером Snowball (Porter2). Чтение
документов, нормализация, построение индекса, сжатие и поиск реализованы на C++.
Python используется только для получения готовых библиотек Arrow, сборки и
интеграционных тестов.

## Быстрый запуск

Из корня проекта, macOS с установленными Command Line Tools:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-build.txt
make
make test
```

Нужны Python 3.9+ и C++17. `pyarrow==21.0.0` поставляет заголовки и динамические
библиотеки **Apache Arrow C++ / Parquet C++**. Исполняемый файл не запускает Python
и не использует Python API. Каталог библиотек записывается в `rpath`; после
переноса проекта или окружения следует пересобрать бинарный файл.
На macOS используются системные ICU (`libicucore`) и zlib. На Linux дополнительно
нужны ICU и zlib development headers/libraries и `pkg-config` (например, пакеты
`libicu-dev`, `zlib1g-dev`, `pkg-config`, `gcc`, `g++`, `make`). На Linux сборка в этой сессии не проверялась.
Официальные C-исходники Snowball 3.0.1 включены в `third_party/snowball`
вместе с BSD-лицензией; они компилируются локально и вызываются из C++.

В текущем рабочем каталоге уже собраны `build/release/l0`, `build/release/l0_tests`
и проверочный индекс `indexes/fineweb-ranked-smoke` на первых **10 000** исходных
документах, отсортированных по `score`. Старый `indexes/fineweb-smoke` имеет
несовместимый формат версии 1; новые бинарные файлы требуют перестроить старые индексы.

```sh
build/release/l0 search --index indexes/fineweb-ranked-smoke \
  --query '(science OR education) AND NOT fiction' --count --limit 10

build/release/l0 search --index indexes/fineweb-ranked-smoke \
  --query 'climate NEAR/5 change' --count --json

build/release/l0 search --index indexes/fineweb-ranked-smoke \
  --query '"united states"' --count
```

Построение индекса **всего** среза (без ограничения числа документов):

```sh
build/release/l0 build --input fineweb-edu --output indexes/full --memory-mb 256
```

Путь `fineweb-edu` автоматически разрешается в
`fineweb-edu/data/CC-MAIN-2014-10`. Можно передать этот подкаталог непосредственно
или отдельный `.parquet`. Файлы обходятся в лексикографическом порядке,
документы внутри — в порядке строк. Это исходный порядок для разрешения равных
оценок. До присваивания docID весь выбранный набор сортируется по убыванию `score`.
Если есть колонка `dump`, её значение проверяется: другой срез отклоняется.

Для короткой проверки с новым каталогом:

```sh
build/release/l0 build --input fineweb-edu --output indexes/sample \
  --max-docs 10000 --memory-mb 64 --sort-memory-mb 4 --batch-size 256
```

`--max-docs 0` означает весь корпус. `--max-docs N` выбирает **первые N исходных
строк**, затем сортирует этот набор; это не выбор N лучших документов всего среза. Каталог назначения должен **не существовать**:
готовые и незавершённые индексы не перезаписываются. При ошибке остаётся каталог
диагностики без готового `manifest`; выберите новый каталог для повторного запуска.
Возобновление прерванной индексации не реализовано.

## Обработка документов

- Через `parquet::arrow::FileReader` читаются `text`, `id`, `url`, **`score`** и `dump`;
  `RecordBatchReader` выдаёт ограниченные пакеты строк. Остальные колонки не нужны.
- ICU выполняет полный Unicode case folding: `Hello → hello`, `Straße → strasse`,
  `ЁЖ → ёж`. Токен — последовательность Unicode-букв/десятичных цифр с
  присоединёнными комбинируемыми знаками. Пунктуация и пробелы разделяют токены.
  Некорректный UTF-8 заменяется разделителем U+FFFD.
- После case folding к токенам из букв `a-z` применяется **официальный Snowball
  English (Porter2), версия 3.0.1**: `running/runs → run`,
  `studies/studying/studied → studi`, `connected/connections → connect`.
  Основа может не быть словарным словом: это стемминг, а не лемматизация.
  Числа, смешанные токены и слова вне `a-z` сохраняются после case folding.
  Английский алгоритм выбран для английского корпуса FineWeb-Edu.
- Координаты нумеруются с нуля. Каждый исходный токен даёт ровно один терм,
  поэтому стемминг сохраняет расстояния для `NEAR`/`ADJ`. Стоп-слова сохраняются.
  NFC/NFKC и удаление диакритики не выполняются.
- Одинаковый токенизатор применяется к запросам и документам. Версия алгоритма
  стеммера и версия Unicode ICU сохраняются в манифесте; несовпадение запрещает поиск.
- `null`/пустой `text` даёт документ без термов; ID документа всё равно сохраняется.
  Результат содержит внутренний `doc_id`, исходный `id`, URL, путь Parquet и номер
  строки в файле, а также исходный **`score`** с точностью `double`.
  Полный исходный текст в готовом индексе не дублируется.

## Исходное ранжирование по score

Ранг задаётся исходным вещественным полем **`score`**, без округления и без замены
на `int_score`. Документ с большим `score` получает меньший docID и предшествует
документам с меньшим `score` во всех выдачах, в которых оба документа совпали
с запросом. При равенстве сохраняется порядок файлов и строк. Пустой текст также
участвует в ранжировании. Колонка `score` обязательна: отсутствие, `null`, NaN,
бесконечность и тип, отличный от float32/float64, приводят к ошибке сборки.

Сортировка выполняется **до токенизации и построения posting lists**:

1. Parquet читается последовательно. Текст и метаданные каждого документа
   временно сжимаются zlib; ключ сортировки содержит `score` и исходный порядковый номер.
2. Порции до порога `--sort-memory-mb` сортируются и сохраняются в `<output>/.ranking`.
3. Выполняется k-путевое слияние, не более 32 входных потоков одновременно.
   При большем числе порций нужны промежуточные проходы.
4. Глобально упорядоченные документы передаются в `Builder`, который присваивает
   docID и проверяет невозрастание `score`, в том числе между сегментами.

`--sort-memory-mb` по умолчанию равен `--memory-mb`; это приблизительный порог,
к нему добавляется память Arrow, текущего документа и голов потоков слияния.
Временные данные требуют дополнительного места на диске наряду с готовым индексом.
Исчерпанные порции удаляются; при штатном завершении и обработанном исключении
сортировщик очищает собственный каталог. После аварийного завершения процесса
временные файлы могут остаться внутри незавершённого выходного каталога.

Все итераторы уже выдают docID в порядке ранга. Поэтому `--limit K` возвращает
первые K совпадений с наибольшим исходным score, включая `OR`, `AND NOT`, `NEAR`
и запросы, проходящие через несколько сегментов. Запрос определяет множество
совпавших документов, а исходный score — их порядок.

## Индекс и выполнение запросов

**Построение.** SPIMI: хеш-таблица `терм → документы → координаты` накапливается
до порога `--memory-mb`, затем записывается отдельный неизменяемый сегмент.
Сегменты охватывают непересекающиеся последовательные диапазоны docID.
Порог оценивает память словаря и posting vectors; это **не жёсткий предел RSS**:
Arrow, текущий документ, Unicode-буферы и временные буферы сжатия требуют
дополнительной памяти. Документ целиком принадлежит одному сегменту.

**Словарь.** Битовое сжатое префиксное дерево Patricia, а не хеш-таблица при
поиске. Байты UTF-8 представлены девятью битами `1 + 8 бит байта`, конец ключа —
нулевым битом. Это различает ключи-префиксы (`a`, `ab`, `abc`). Внутренний узел
содержит номер различающего бита и два индекса потомков; лист — запись терма.
После обхода проверяется полное совпадение ключа. Дерево содержит `2T−1` узлов
для `T > 0` термов и хранится на диске, без восстановления указателей при загрузке.

**Posting lists.** Отсортированы по docID, разделены на блоки до **128 документов**.
DocID кодируются разностями, первый docID каждого блока — абсолютный. Координаты
кодируются разностями отдельно внутри каждого документа. Частоты термов также
сжимаются. Блок можно распаковать независимо от предыдущих.

**PForDelta / P4Delta.** Собственная реализация patched frame-of-reference:
для каждого блока целых выбирается ширина `b ∈ [0,32]`, минимизирующая размер
упакованных младших битов и исключений. Обычные значения хранятся в `b` битах;
исключение хранит индекс элемента и ненулевые старшие биты в unsigned varint.
После восстановления исключений применяется обратное delta-преобразование.
Это вариант формата PForDelta с собственным представлением исключений, **не**
бинарно совместимый с FastPFor. Кодируются и полные, и неполные блоки.

**Skip lists.** Базовый уровень содержит максимальный docID и смещение каждого
блока. Верхние уровни хранят ссылки на концы групп из 8, 64, 512, … блоков.
`ADVANCE(target)` спускается по уровням, пропускает блоки, максимум которых меньше
цели, распаковывает только выбранный блок и делает `lower_bound` внутри него.
Связи представлены индексами массивов, без адресов памяти. На уровне требуется
не более примерно восьми проверок; сложность поиска блока — `O(log₈ B)`.

**Диск и загрузка.** Сегменты и таблица документов читаются через read-only
`mmap`; словарь и posting lists не копируются целиком в RAM. Смещения — 64-битные,
docID и координаты — 32-битные; `UINT32_MAX` зарезервирован как конец итератора.
Формат явно little-endian, без сериализации C++ struct padding. Проверяются
размеры и границы при чтении. Готовый `manifest` появляется через переименование
после закрытия всех файлов; незавершённый индекс не открывается. Контрольные суммы
и гарантия сохранения при потере питания не реализованы.

**План выполнения.** Итераторы возвращают отсортированные docID, предоставляют
`next`, `advance`, оценку стоимости и позиционные интервалы. Последовательности
`AND` объединяются в многопутевое пересечение и сортируются по document frequency:
сначала обрабатывается редкий терм. `OR` сливает потоки без дублей; `AND NOT`
продвигает исключающий итератор к текущему docID левого. Промежуточные полные
множества документов не материализуются. Координаты распаковываются только для
позиционных запросов и только после совпадения docID. `NEAR`/`ADJ` соединяют
отсортированные интервалы с поиском начала подходящего диапазона. Для вложенных
позиционных выражений сохраняются все уникальные интервалы совпадений.

Сегменты обрабатываются последовательно, результаты уже упорядочены глобально.
Финальное слияние сегментов не требуется. Очень большое число маленьких сегментов
увеличивает цену поиска; увеличивайте `--memory-mb`, если позволяет RAM.
Чрезвычайно частые позиционные выражения могут порождать много интервалов внутри
одного документа — время и память зависят также от числа таких совпадений.

## Язык запросов

Операторы пишутся **в верхнем регистре**, регистр термов не важен. Между
самостоятельными выражениями нужен явный оператор. Приоритет, от высокого к низкому:

1. Скобки, термы и фразы в двойных кавычках.
2. `NEAR`, `NEAR/n`, `ADJ`, `ADJ/n`.
3. `AND`, `AND NOT`.
4. `OR`.

Операторы одного приоритета левоассоциативны.

| Запрос | Значение |
|---|---|
| `science AND research` | Оба терма в документе |
| `science OR research` | Хотя бы один терм |
| `science AND NOT fiction` | Первый терм есть, второго нет |
| `(science OR education) AND research` | Произвольная булева комбинация |
| `climate NEAR/5 change` | Любой порядок, разность ближайших координат от 1 до 5 |
| `climate NEAR change` | То же, расстояние по умолчанию 5 |
| `united ADJ states` | `states` непосредственно после `united` |
| `education ADJ/3 research` | Упорядоченные термы, разность координат от 1 до 3 |
| `"united states of america"` | Точная последовательность нормализованных термов |
| `(solar OR wind) ADJ energy` | Альтернативы внутри позиционного выражения |
| `(new ADJ york) NEAR/5 university` | Расстояние от края найденного интервала |

Расстояние считается в **токенах**, а не символах; непосредственно соседние слова
имеют расстояние 1. Для интервалов сравниваются ближайшие края. Перекрывающиеся
интервалы не соединяются: `word NEAR/1 word` требует двух разных соседних
вхождений. `ADJ/n` сохраняет порядок левого и правого операндов. Позиционными
операндами могут быть термы, фразы, другие позиционные выражения и их `OR`.
`(a AND b) NEAR c` отклоняется: у обычного булева `AND` не определена координата.
Отрицание поддерживается в форме `AND NOT`; унарного `NOT` нет.

Фразы токенизируются и стеммируются тем же способом: `"run dog"` находит
`Running dogs`. Это совпадение нормализованных термов, без учёта исходных словоформ.
Дефис разделяет токены, поэтому `"well-being"` эквивалентно запросу `well ADJ being`.
Для поиска слова, совпадающего с оператором, используйте кавычки: `"AND"`.
Пределы парсера — 512 узлов AST, 64 уровня скобок и 64 КиБ текста запроса.

## CLI и проверка

```sh
build/release/l0 --help
build/release/l0 stats --index indexes/fineweb-ranked-smoke
build/release/l0 document --index indexes/fineweb-ranked-smoke --doc-id 0
build/release/l0 repl --index indexes/fineweb-ranked-smoke --count
```

`--limit 20` ограничивает число выводимых документов. Без `--count` поиск
останавливается по лимиту и сообщает нижнюю границу числа совпадений
(`complete=false` в JSON). С `--count` подсчитываются все результаты,
но выводятся только первые `--limit`. `--count --limit 0` — только подсчёт.
Результаты содержат `score`; текстовый вывод использует колонки
`doc_id`, `score`, `id`, `url`. Время поиска не включает открытие индекса и печать результатов.

```sh
.venv/bin/python -m pip install -r requirements-test.txt
make test          # codec, stemming, ranking, trie, iterators, randomized oracle
make sanitize      # те же тесты под AddressSanitizer + UndefinedBehaviorSanitizer
make integration   # C++ читает сгенерированные Parquet, проверяется CLI
.venv/bin/python tests/integration.py \
  --real-index indexes/fineweb-ranked-smoke --real-docs 10000
```

Последняя команда ожидает индекс первых указанного числа исходных документов
среза, предварительно отсортированных по `score`. Python-версия Snowball 3.0.1
из `requirements-test.txt` служит независимой реализацией для сравнения с C-кодом.
Проверка читает исходный Parquet и сравнивает **полные списки docID**
для десяти запросов, включая фразу, `NEAR`, `ADJ`, повторяющиеся термы и булевы
комбинации. В C++ тестах — случайные раунды сжатия, 350 запросов против независимого
наивного интерпретатора, точные множества позиционных интервалов, многосегментность,
пустой корпус и словарь, повреждения формата и случайные `ADVANCE` на 18 000 документах.
Отдельно проверяются известные основы Porter2, сохранение координат, многоэтапное
слияние 95 порций, стабильные равные оценки, ранговые docID между сегментами,
некорректные score, очистка временных данных и отказ открытия старого формата.

Результаты проверки в этой рабочей среде: **45 497** C++ проверок прошли в release
и под ASan/UBSan; интеграционные тесты и все десять запросов по реальному срезу
совпали с эталоном. В `fineweb-ranked-smoke`: 10 000 документов, 8 011 694 токена,
3 сегмента, **39 874 726 байт** вместе с метаданными. Полный срез содержит
14 Parquet-файлов и 10 987 331 документ; полный индекс в этой сессии не строился.
Результаты малого прогона не являются измерением производительности всего среза.

|---|---|

| `src/tokenizer.cpp` | Case folding, токенизация, Snowball English |
| `src/ranking.cpp` | Внешняя сортировка документов по score до индексации |

| `src/index.cpp` | SPIMI, Patricia, skip lists, mmap, posting iterator |
